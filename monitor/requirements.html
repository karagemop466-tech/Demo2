Questions, known answers, and missing information

1. Which endpoint and environment should be used?

Known answer: The request specifies Kalshi demo. Official docs recommend https://external-api.demo.kalshi.co/trade-api/v2 for REST and wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 for WebSocket; shared demo hosts remain supported.

Missing: Nothing for public market-data host choice. This site intentionally never switches to production.

Kalshi API environments ↗

2. Is there a demo account or API key attached to this work?

Known answer: No account identifier, API key ID, signing key, portfolio response, or authorized session was present in the repository or task context. The existence or balance of any personal demo account is unknown.

Missing: An authenticated, server-side integration and explicit account authorization. The site does not request or store credentials.

Kalshi API key guide ↗

3. What should “highest dollar amount” measure?

Known answer: The dashboard clearly labels its current choice: visible resting bid-side notional from the orderbook. It does not call contract volume “dollars.”

Missing: Whether the intended sort is displayed depth, executed turnover, open interest, or another measure. No official event-level dollar-volume definition was verified in the source review.

Orderbook reference ↗ Market data fields ↗

4. How should the five topics be classified?

Known answer: Kalshi’s event response exposes descriptive metadata including category, title, subtitle, and series ticker. The current project uses a transparent local keyword filter.

Missing: An approved mapping of Kalshi series/category values to “gas prices,” “elections,” “culture,” “crypto,” and “golf,” plus whether to include adjacent topics. Current matching can miss or over-include events.

Event metadata reference ↗

5. When should a result count as resolved?

Known answer: Kalshi documents distinct determined and finalized states; the result can be known while the market is still awaiting settlement and can be disputed. The watchlist shows the API result and status separately.

Missing: Whether the user wants “result announced” (determined) or “settlement complete” (finalized) as the stop condition. The watchlist does not auto-delete tracked events.

Market lifecycle guide ↗

6. What does portfolio “performance” mean?

Known answer: Kalshi provides separate balance, positions, fills, and settlement data. The dashboard has not combined these account-specific endpoints without access.

Missing: Starting cash/baseline, deposits and transfers treatment, realized versus unrealized P&L, fee inclusion, time window, and account/subaccount scope.

Balance ↗ Fills ↗ Settlements ↗

7. Which trade types and risk limits are permitted?

Known answer: No user-approved order size, side, price, time-in-force, loss limit, exposure limit, or strategy was available. No trades were sent.

Missing: Account-specific permission and an explicit risk-control policy, plus secure server-side request signing and a tested confirmation/cancel workflow.

Create Order reference ↗ Key permissions ↗

8. How should fills be categorized and strategy performance measured?

Known answer: No user-approved trade tags, strategy names, attribution rules, performance baseline, or account fills were supplied. Market topic alone does not establish trade intent.

Missing: Choose whether tags are manually assigned or rule-assisted, whether they can be edited, how strategy versions are tracked, and which performance measures and time windows are approved. Preserve official fill and settlement fields so labels do not replace source data.

Get Fills ↗ Get Settlements ↗

9. How long should event and account history be retained?

Known answer: Kalshi partitions certain live market, candlestick, trade, order, and position data into historical endpoints after their respective cutoffs. The local watchlist survives only in the current browser’s storage.

Missing: Required retention period, export format, cross-device sync, and a durable backend/database. Event APIs can omit nested markets that have moved to historical storage.

Historical data guide ↗

10. Can the browser make live API requests from GitHub Pages?

Known answer: The app is coded to make read-only REST requests directly to the recommended demo host and to show an explicit error instead of placeholder values.

Missing: Browser CORS, current API availability, and actual live responses could not be verified from this workspace. This is flagged for post-deploy browser testing.

Official public event endpoint ↗ GitHub Pages docs ↗
