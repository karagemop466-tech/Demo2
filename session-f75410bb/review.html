Verified findings and irregularities

ID / statusCode evidence and impactOfficial source
R1
Needs review · blocker		 server/index.js builds a legacy-shaped order object (market_ticker, buy/sell, outcome_side, price_dollars, type); server/kalshiClient.js POSTs it to /orders. A mocked fetch reproduced that exact URL and JSON body. The documented Create Order (V2) route is POST /portfolio/events/orders and its body uses ticker, side: bid|ask, price, and time_in_force. The current backend's real order path/body therefore does not match the official V2 API; successful execution is not verified and should not be represented as working until corrected and tested with a demo account. Create Order (V2)
R2
Needs review · coverage		 server/index.js calls getEvents with a fixed limit of 200 and does not iterate or return the event cursor. The official response includes a cursor; the live backend's top-event list and automatic tracker therefore cannot claim complete enumeration when more pages exist. Handle pagination before treating rankings or tracked events as a full list. Get Events
R3
Partial · needs review		 The newer root site now has pages/live-alerts.html with two scrolling feeds and ≥$0.10 moves. The two feeds load collected data/jumps.json and data/snapshot.json once at page load; there is no timer, streaming connection, or runtime refresh. "High ROI" is an explicitly rule-based move-size + estimated-volume filter, not a predictive model. It is a useful snapshot alert page, but it does not yet meet the real-time or model-selected feed wording of the request. Get Trades · WebSocket quick start
R4
Needs review · coverage		 The backend requests only one page in its periodic event poll. WebSocket market-data channels can provide updates, but the official handshake is authenticated; a static browser cannot safely hold the private signing key. Use a secured backend for an authenticated WebSocket, with explicit REST fallback/staleness state. This audit did not verify the current demo account's WS connectivity. WebSocket handshake and channels
R5
Needs review · deployment boundary		 The project contains several independently built dashboard trees and workflows (documented in the repository coordination log). GitHub Pages serves static files only; it does not run server/index.js. Authenticated portfolio and trade features require separately deployed backend infrastructure and demo-only credentials. No credentials were added or used here; account balances and live order execution remain unverified. GitHub Pages · Demo environment · API keys
R6
Needs review · data join		 DOM smoke test with the committed files rendered 14 alert rows, but 0/14 tickers matched between data/jumps.json and data/snapshot.json. As a result, topic/title/volume metadata are absent in the UI, the default High-ROI feed shows 0 rows, and six snapshot-move rows have no source link (rendered as “—”). The jump data is sourced from data/dashboard_instrument.json, while the page joins against the separate canonical data/snapshot.json. Use a coherent dataset/provenance and ensure every alert row retains its official source. The jump records themselves include topic/title fields for most rows, but the page does not use those fields as a fallback. Get Markets · Get Trades
R7
Needs review · freshness		 At this checkout, data/snapshot.json says 2026-11-20T14:10:44Z, while data/jumps.json says its source snapshot was 2026-11-20T19:49:16Z. The page's visible “Snapshot” status uses the older file, while its alert generation line is 2026-11-20T19:49:16Z. Show a single generation timestamp matching the actual joined data and mark stale/mismatched feeds. Get Markets · Get Trades
R8
Verified caveat		 Orderbook outputs are bid ladders for YES and NO. The dashboard derives implied asks using binary-price parity; derived asks are not observed ask-side depth. UI labels and tests explicitly distinguish those derived values. Keep this distinction visible to avoid presenting an inferred ask as resting liquidity. Get Market Orderbook

Verification performed

  • npm test: 8/8 tests passed (topic filters, active/resolved market selection, orderbook arithmetic and derived asks, resolution labels, HTML escaping, chart timestamps/missing points).
  • npm run check: 15 HTML pages; local references resolved; source-linked rows, unique IDs, and no inline handlers.
  • npm run build: generated 15 static pages.
  • python3 tools/check.py: links/nav/data/secrets/scripts passed across 18 pages; it reported 11 non-2xx snapshot API requests (the existing Verification page is the indicated evidence location; this audit did not re-fetch or reclassify each one).
  • python3 scripts/check_links.py: 8,455 references across 124 HTML files, all resolved on the current integrated tree.
  • JSDOM smoke test ran the merged live-alerts page against the committed snapshot files: 14 rows rendered, 0/14 with a matched market/topic, 0 high-ROI rows, and 6 rows without a per-row source link. It also exposed mismatched snapshot timestamps. These are published here as verification findings, not silently corrected.
  • Kalshi demo, event-list, orderbook, candlestick, order V2, WebSocket, and GitHub Pages documentation pages were read directly. A mocked request confirmed what the backend currently emits; no private key, live account, or order call was used.

Recommended follow-up

  1. Update the backend order route and request shape against Create Order (V2); add a mocked contract test and require explicit demo-only configuration before any execution.
  2. Paginate event discovery using the official cursor and show completeness/last-refresh state.
  3. Implement two distinct scrolling feeds: all confirmed threshold moves and a transparently scored model shortlist. Label the ROI score as experimental; do not call it predictive without out-of-sample evidence.
  4. Preserve original price points and publish each alert's ticker, direction, delta, timestamp, source link, and cause as blank/unverified unless separately confirmed.
  5. Consolidate navigation to one primary dashboard, while retaining the audited historical research pages as clearly identified supporting material.
