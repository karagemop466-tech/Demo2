Flagged for review

Irregularities found in the official Kalshi demo data and documentation, constraints that could not be resolved from this environment, and issues found in the repository. Nothing here blocks the site, and nothing here has been silently corrected — each item keeps the value that was actually observed.

A · Irregularities in the official data or documentation

IDAreaWhat was observedWhy it mattersSourceStatus
F1Settlement sources Placeholder text left in source names, for example “official government sources of ”, “local news outlets with verifiable mastheads in ”, “their official campaigns or representatives”, each pointing at https://kalshi.com/. The named resolution source is unclear, so the outcome of those markets cannot be independently checked. /series Needs review
F2Settlement sources Some demo series list search-engine results and unrelated data pages as settlement sources — for example a Google search link and an energy-information page attached to a market about banning a product. A search page is not a primary source for a contract's outcome. /series Needs review
F3Demo vs production The same series shows different metadata in the two environments: the demo fee_type is quadratic while production is quadratic_with_maker_fees; the demo contract_url points at a staging S3 bucket while production points at assets.kalshi.com; last-updated dates differ. Fee assumptions and contract documents taken from one environment may not hold in the other. demo /series/KXAAAGASM Needs review
F4Documentation GET /markets documents the status filter values as unopened, open, closed, settled, while the market schema documents initialized, inactive, active, closed, determined, disputed, amended, finalized. Actual responses carry active and finalized. Filtering on a documented response value can return nothing; the site filters on the documented query values instead. Get Markets Needs review
F5Price data A market reported last_price_dollars of $0.50 while its live quote was a $0.23 YES bid and a $0.24 YES ask — the $0.50 print came from an earlier candle. Last price can be stale; using it as an entry or mark would mislead. candlesticks Needs review
F6Liquidity One market showed large open interest with a one-sided quote (best YES bid $0.00, best YES ask $1.00). Entry and exit are difficult when the book is one-sided; such markets are not good candidates for a strategy. /markets Needs review
F7Missing metadata Some crypto series have an empty contract_url, a null settlement_sources, and a contract_terms_url with no file name. Incomplete contract documentation for those series. /series Needs review
F8Demo-only data The demo environment contains synthetic contracts: “1+1 = 3”, “Demo only” BTC one-minute markets, and markets whose strike is literally “demo strike”, with close dates in 2099. Demo outcomes are not evidence about real events, and these rows would distort any statistic computed from demo fills. /markets?status=settled Needs review
F9Category mapping “Gas prices” and “Golf” are not API categories. Gas maps to Commodities (tag “Oil & Gas”) and Economics (tag “Oil and energy”); Golf is the tag “Golf” under Sports; “Culture” is not a published category and maps to Entertainment. The topic names in the request are editorial labels, not official ones. Every row on the category pages states which basis was used. taxonomy Needs review
F10Dollar amounts There is no dollar-turnover field. volume_fp, volume_24h_fp and open_interest_fp are contract counts. “Highest dollar amount” cannot be read directly; the site uses the labelled estimate volume_fp × last_price_dollars everywhere it ranks. Get Markets Needs review
F11Titles Some market titles contain Markdown bold markers, for example “Will average **gas prices** be above $4.18?”. Cosmetic only; titles are shown as the API returns them rather than being rewritten. /markets Minor
F12Timing A gas contract closes at 03:59 UTC on the measurement date, so trading stops before the published AAA reading is taken for that day. Any timing or "trade to the print" strategy has to account for it. /markets Needs review
F13Settlement sources An event and its series list the same source name with different URLs (for example “The Washington Post” pointing at a different publisher's domain), and the event list also contains a URL that does not match its name. Name and link disagree, and event and series disagree. /events Needs review
F14API reliability One market request returned HTTP 502 during an earlier collection and was not retried successfully. There can be gaps in a snapshot for that series; the collection log records every attempt and status. collection_log.json Minor
F15Link hygiene A settlement URL in a crypto series carries a marketing tracking parameter. Cosmetic; the link is reproduced as published. /series Minor
F16Caching Kalshi states that responses are cached for a short time, so prices, sizes and status can lag the exchange by several seconds, and filtered listings can lag longer than a single-market read. The live table can be a few seconds behind the exchange — the chart is affected more than the table. Get Markets Noted
F17Historical coverage Markets that settled before the historical cutoff are only available through GET /historical/markets, and candlesticks for them through GET /historical/markets/{ticker}/candlesticks. The “resolved markets” table can only cover the recent window that the live endpoint returns. Historical data Needs review
F18Model semantics Market records carry notional_value_dollars of $1.0000 and expiration_value of $0.0000. These are the contract's settlement values, not traded dollar volume. Easy to mistake for a turnover figure; the site never ranks on them. /markets Needs review

U1Portfolio, balance and trade execution Require a Kalshi demo API key. No account existed in the build environment, so no account value was obtained and no trade was placed. C · Repository irregularities

IDWhat was foundWhy it mattersResolution
R1 Earlier versions of this repository contained a client-side page that pasted a Kalshi private key into a public GitHub Pages page and signed requests with it. A private signing key entered into a publicly served page is a credential-exposure risk, whatever the transport encryption. The current site offers a local command-line signer (tools/kalshi_trade.py) as the primary path, and the browser signer is opt-in, memory-only, and clearly labelled. Recorded as suggestion S7 and question Q1.
R2 Two independent implementations of the dashboard existed in the repository at once (a root-level index.html with app.js/style.css, a pages/ set with assets/, and a verified/ subsite with its own stylesheet and scripts). Duplicate navigation, two live dashboards and two sets of numbers on one public site invites confusion about which one is authoritative. This integration session consolidated them into one site: root index.html plus pages/ and assets/. The superseded copies are removed in the final change set, and their verified rows, flags and questions are carried forward here and on the other pages.
R3 The pages.yml workflow published the whole repository root, so any file added to the repository root became publicly served. Working files or credentials accidentally placed at the root would be published. The workflow still publishes the root, but the root now contains only the site, the data snapshot, the tools and the coordination log; a .gitignore keeps bytecode caches out and no secret is stored in the repository.
R4 README files in earlier sessions described different site layouts and different capabilities, and in one case documented a key-pasting flow that was later removed. A README that disagrees with the code is a trap for the next person. The README was rewritten to match the consolidated site, and the historical descriptions are preserved in COORDINATION.md and in the git history.
R5 Several sessions pushed branches and pull requests to the same repository at the same time, and COORDINATION.md was edited by more than one session. Merge conflicts and duplicated or contradictory pages. Every session's claim, verification record and irregularity list is kept in COORDINATION.md; this session rebased on origin/main before pushing and resolved the one conflict in that file by keeping both sides.
R6 The scheduled collector commits directly to main, so a data refresh lands on the production branch without a review. A bad snapshot would publish itself. Accepted deliberately: the collector only writes data/*.json, it is idempotent, and every write is attributable to the bot commit. The alternative — a pull request per refresh — is offered as suggestion S5 for review.
How to use this page. Each row tells you what was seen, why it could matter and where to check it yourself. When you have decided what should change, record it on the Suggestions board and, if it changes a number on the site, state the rule that should replace the current one.
