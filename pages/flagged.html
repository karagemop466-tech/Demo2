Flagged for review

Irregularities, gaps and judgement calls found while building this site. None of these blocked publication; each is stated with its impact, the mitigation actually in place, and the official source that frames it. Review this page first if something on the dashboard looks wrong.

#FindingWhy it mattersMitigation in placeSourceStatus
F1Sandbox egress to Kalshi is blocked
The authoring sandbox’s TLS handshake to external-api.demo.kalshi.co fails (SSL_ERROR_SYSCALL), so the collector could not be proven from inside the sandbox.		Any “live” number would have been unverifiable.Moved collection to GitHub Actions, which has normal egress, and made every snapshot carry an HTTP-status log. The workflow fails loudly rather than publishing an empty snapshot.demo_envopen for review
F2No dollar-volume field exists
The Trade API exposes contract counts (volume_fp, open_interest_fp) and prices, but no traded-dollar-volume field.		Ranking by “highest dollar amount” cannot be sourced exactly.Dashboard shows the estimate volume_fp × last_price_dollars, tags it est., and offers volume-only and open-interest-only sorts beside it. Raised as Q1 / S1.get-marketsopen for review
F3Order book has no ask side
The endpoint returns yes bids and no bids only.		Naive code would show a book with no offers and a false spread.Ask depth is derived as 1 − p from no bids and labelled derived everywhere it appears, including the spread.get-market-orderbookopen for review
F4Legacy order endpoint returns 410 Gone
The previously published build posted to POST /portfolio/orders, which the docs now mark removed and which returns 410 with deprecated_v1_order_endpoint.		Trade execution would have failed silently for every user of that page.Rewritten against POST /portfolio/events/orders with the documented required body fields. Logged as a correctness defect in the repo review (R3).create-order-v2open for review
F5Demo prices may not reflect real markets
Kalshi states this explicitly as a warning on the demo page.		Any strategy derived from demo fills may not transfer.Warning shown on every data page; strategies are labelled demo-only; Q7 / S6 ask for an explicit policy decision.demo_envopen for review
F6No demo API key is configured
Portfolio, P&L and execution need a signed request with a demo key pair.		Those pages cannot show real figures.They show an explicit “not configured” state rather than zeros, with the exact secret names required. Raised as Q4 / S4.api_keysopen for review
F7Demo data contains synthetic test markets
Verified live: KXQUICKSETTLE-20NOV26H0550-3 is titled “1+1 = 3” with rules “If 1+1 equals 3 … resolves to Yes”, KXDEMOFUTHOURLY- markets are explicitly labelled Demo BTC, and some events carry placeholder strikes such as {"demo strike": "demo strike"} with close dates in 2099.		Averaging over synthetic markets produces meaningless statistics.Nothing is excluded silently: these markets fall outside the five topics because they carry no in-scope tag or category, and the unmapped-series list is published for review.get-marketsopen for review
F8Snapshot freshness is 10 minutes, not real time
Data is refreshed by a scheduled GitHub Actions run.		Short chart windows are often empty; the word “live” overstates it.Labelled on the dashboard, the empty state explains why, and S3 offers a relay as a decision.quick_start_websocketsopen for review
F9Unmapped series are excluded, not guessed
Any open event whose series has no in-scope tag/category is dropped from the tables.		In-scope markets could be missed if Kalshi tags a series unusually.The collector publishes the full list of unclassified series in the snapshot for review, and data/snapshot.json keeps the series inventory with tag counts.get-series-listopen for review
F10Some demo series carry unreviewed metadata
Demo series responses include staging S3 hostnames (e.g. kalshi-public-docs-staging.s3...) in contract_url, and repeated placeholder settlement-source strings.		Contract links from demo records are not always stable or final.Links are surfaced as returned, with the production docs link provided as the authoritative reference on the same row.get-series-listopen for review
F11Candlestick traded price is empty in quiet periods
Verified live on KXPGATOUR-THRC26-LABE: several candlesticks return "price":{} because no trade occurred in that period, while the bid and ask closes are still present. Periods with no activity can be omitted from the response entirely.		Plotting the traded price alone leaves gaps, or an empty chart, on thin demo markets.The chart defaults to a derived quoted mid = (yes bid close + yes ask close) / 2, labelled “derived”, and keeps “last trade” as an explicit option that shows its own gaps. The collector stores both, so nothing is interpolated.get-market-candlesticksopen for review
F12A topic can exist in the catalogue with no live markets
Verified live: DIESEL and DIESELM are the Gas-tagged series, but the demo environment has no open events or markets for either. Elections, culture, crypto and golf do have live markets.		An empty Gas page would look like a bug rather than a fact about the demo exchange.The collector records series_in_catalog and series_with_live_markets per topic, and the Gas page states “catalogue only — 2 series exist, none has a live market”. Gas stays in scope and populates automatically when the demo exchange lists those markets.get-series-listopen for review
F13Sharp-jump cause cannot be determined from the API
The dashboard now marks price moves ≥ $0.10 between consecutive points on the live chart and links each to the market’s page on Kalshi, plus a clearly labelled “possible context” search link. But the Trade API returns price and volume only — no news, no event, no explanation for why a contract moved.		A reader could mistake a jump marker for a confirmed causal event.Each jump row links to the market on Kalshi (where traders can see discussion) and is tagged cause unverified; the search link is labelled “not an official source”. Nothing is inferred. Raised as verification row on pages/verification.html and as suggestion S9 on pages/suggestions.html.get-markets, get-tradesopen for review
F14Browser-side private-key prompts are unsafe on a public static host
Session 6d75123b’s live/trading.html Mode B asked the user to paste a demo private key into the page, and assets/app.js still carried orphaned WebCrypto signing code wired to ids no page contains. PR #6 (session 22b4f0cb) raised this and was stale; session bdb4d2d0 took it over under the 60-minute rule.		A public GitHub Pages deployment cannot protect a pasted signing key; any script on the page could read it. This conflicts with the README policy that signing keys belong only in repository secrets behind the three execution gates.Integration fix (2026-11-20): the Mode B credential form is disabled on the deployed copy with a notice pointing at the gated Actions path (tools/execute_strategy.py) and the server/ backend; the orphaned signing code was removed from assets/app.js. Mode A paper trading and the request builder are unchanged. Reversible by removing the disabled attributes when serving privately. Cross-scope request logged for session 6d75123b in COORDINATION.md.api_keysopen for review

How to spot these in the data

  • F2: any figure tagged est. is computed, not returned.
  • F3: the ask column says derived; the raw response has only bids.
  • F6: the portfolio page says “not configured”; it is not a zero balance.
  • F11: the chart notes whether it is plotting a derived quoted mid or a traded price.
  • F12: the Gas page says “catalogue only” instead of showing an unexplained empty table.
  • F14: no page on the deployed site accepts a private key; the one form that did is disabled behind a notice that names the gated Actions path.
  • F13: sharp jumps ≥ $0.10 are marked with red vertical markers on the chart and listed in a table below it, each tagged “cause unverified” — the Trade API returns price and volume only, never the news or event behind a move.
  • F8: the dashboard header shows the snapshot time and age, so stale data is visible.
  • F9: compare the in-scope series list per topic against the unclassified list in data/snapshot.json.
  • N-1: the snapshot states its own cap and its published-vs-universe counts; a topic at the cap is bounded, not complete.
  • N-3: every fee is tagged as a model with the 0.07 constant, not as an exchange figure.
  • N-4: short-dated rows are tagged source_pass: near_term in the snapshot.
  • N-7: every alert line is tagged live poll or snapshot; the model screen is a filter with printed thresholds, never a forecast.

Collector and desk findings (session 7085e643, 2026-11-20)

Findings from the collector bounds and the simulated desk work. Each row states what was changed and what is still a judgement call, so a reader can tell a bounded file from a complete one, and a modelled fee from an exchange-confirmed one.

#Irregularity / gapImpactAction taken / statusSource
N-1The published snapshot is bounded, so it is not the full universe
The snapshot had grown to 111.97 MB, which GitHub rejected at the push step, so six consecutive refresh runs published nothing at all.		A reader could take the tables as the whole of the demo exchange, and no data was reaching the site.Fixed. The collector now applies a publish budget (rows per topic, then a byte budget with a halving loop) and the pre-push tools/guard_sizes.py fails the job before the commit step if any file is over budget. The snapshot carries publish_policy with its cap and coverage with published_markets vs universe_markets, and complete_enumeration: false. Dropped counts are published, not hidden.get-markets
N-2The by_topic copy duplicated the whole payload
20.23 MB of the 47.26 MB snapshot was a per-topic re-slicing of the same rows.		Nearly half of the published file was redundant, and the redundant copy doubled the push size that was already over GitHub's limit.Removed. No page reads it; the topic pages slice data/snapshot.json at render time. Do not re-add it.get-markets
N-3Fees are a model, not an exchange confirmation
The quadratic general form uses the constant 0.07, which is not restated on the docs site, so the figure cannot be confirmed from a published document.		Every fee, and therefore every P&L, is a calculation rather than a reported number.Fees are computed in Decimal and rounded up to six decimals exactly as the fee-rounding page specifies, the multiplier is taken from the series' own fee_multiplier, and every ledger row is labelled fee_basis: “quadratic model, 0.07 constant — not exchange-confirmed”. The page shows that label beside each fee instead of presenting it as a fact.fee rounding, get-series
N-4Near-term rows come from a different request than event rows
The event pagination never returned a market closing inside 90 days, so every time-to-close rule could never fire — the desk legitimately opened 0 trades on a complete-looking snapshot.		A short-dated market would have been invisible, and a 0-trade run would look like a strategy failure. Fixed. A separate pass unions short-dated open markets in through the documented GET /markets?status=open&max_close_ts=<now + window> filter. Rows from that pass are tagged source_pass: “near_term”, and the snapshot reports near_term_markets_added and near_term_window_hours. They are a different request, so they are disclosed as such rather than blended in.get-markets
N-5Resolution rows are gathered per series, so the count is a lower bound
The earlier global status=settled scan returned 0 in-scope rows for 5 hours and the snapshot reported resolved_in_scope: 0.		Resolved markets would have been recorded as unresolved, and the resolution table would have been silently empty. Fixed. The collector now queries each in-scope series with the documented series_ticker=…&status=settled&min_settled_ts=… filter, and keeps a row only when its own event_ticker really belongs to the queried series. Remaining uncertainty: the list is capped per series, so resolved_in_scope is a lower bound and is labelled as such.get-markets
N-6A simulated fill assumes the full size is available
The desk takes the posted ask as executable for the whole simulated size.		A real order could be filled worse, or not at all, so P&L is optimistic.Stated on the page and in every ledger row; the alternative (consulting the order book) is noted as an open improvement, and the desk publishes how many rule matches produced no order and why, so an empty book is visible.get-multiple-market-orderbooks
N-7The alert desk's two streams differ in granularity, and its screen is a heuristic
The dashboard now runs two scrolling chats of ≥ $0.10 swings: all events and model screen — high ROI. Lines come from a browser-side poll of the official demo Trade API (documented tickers= filter) every 20 s, plus a coarser stream derived from the collector's 10-minute tick history. The screen is a deterministic filter over official fields (entry price, 24 h volume, time to close), not a forecast.		A reader could read a “high ROI” line as a prediction, and could not tell which lines are live and which are sampled.Every line is tagged live poll or snapshot, the screen thresholds are printed on the page, and the potential ROI shown is labelled arithmetic rather than a claim. If the live poll is blocked, the desk says so in the status banner and keeps the snapshot stream instead of pretending to be live. Swing comparisons use a 1e-9 tolerance, because 1.00 - 0.90 is 0.09999999999999998 in binary floating point and a real $0.10 move must not be dropped. The “possible context” link is a news search tagged not an official source (same class as F13).get-markets, websockets quick start
