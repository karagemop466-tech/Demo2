Portfolio - demo account

Balance, open positions and fills for the Kalshi demo account, read with a signed request. Signing rules, headers and the pre-sign string are exactly as documented in Quick Start: Authenticated Requests.

Positions

From GET /portfolio/positions?settlement_status=all. Field meanings are listed under the table so no number is ambiguous.

Fills - the raw trade record

From GET /portfolio/fills. Every fill shows the official outcome_side, book_side, price on both legs, fee and whether it was taker or maker.

Executions - what the executor did

From data/executions.json, written by tools/execute_strategy.py. Dry-run entries were validated but never sent. Only entries with an HTTP status were actually transmitted.

Placing a demo order by hand is not required

Execution is driven by data/strategy_plan.json plus the trade.yml workflow and three explicit switches - KALSHI_TRADING_ENABLED=1, a demo key pair, and a per-run notional cap (default $25). The executor refuses any ticker that is not in the collector’s in-scope set, refuses duplicates in one run, and always uses immediate_or_cancel so no order is left resting unattended. Rationale and the exact request shape are on API reference.

Local trading CLI (verified against the current API)

tools/kalshi_trade.py signs every request locally (Ed25519 or RSA-PSS/SHA-256, timestamp + method + path — API Keys). The site never accepts or stores credentials. Order commands use the V2 endpoints (create, cancel; book side bid ≡ yes, ask ≡ no — order_direction).

CommandEndpointPurpose
balanceGET /portfolio/balanceBalance + portfolio value (requires demo key)
positions / fillsGET /portfolio/positions / GET /portfolio/fillsPosition and execution history
orderPOST /portfolio/events/ordersPlace a limit order (fixed-point price/count strings)
cancelDELETE /portfolio/events/orders/{id}?market_ticker=…Cancel a resting order (ticker required for auto-routing)
