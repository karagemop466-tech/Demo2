Part A — Answered from verified official sources

QuestionAnswerSource
Which API do we use? The Kalshi demo environment. REST root https://external-api.demo.kalshi.co/trade-api/v2 (also supported: https://demo-api.kalshi.co/trade-api/v2). WebSocket root wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 (also supported: wss://demo-api.kalshi.co/trade-api/ws/v2). Test in the demo environment · API environments
Does the sandbox reach the API? No. DNS resolves, but the TLS handshake fails (SSL_ERROR_SYSCALL), so data is collected by a GitHub Actions runner and committed to data/; the page then tries a direct browser fetch and falls back to that snapshot. Observed in this environment; the collector and its log are in tools/collect_kalshi.py and data/collection_log.json
Which official categories map to the five topics? Gas prices → category Commodities (tag “Oil & Gas”) and Economics (tag “Oil and energy”). Elections → category Elections. Culture → category Entertainment (there is no “Culture” category in the published taxonomy). Crypto → category Crypto. Golf → tag Golf under category Sports. Official tag taxonomy response · series records
How is “highest dollar amount” measured? It cannot be read directly. The API returns market volume in contracts (volume_fp, volume_24h_fp) and open interest in contracts; no dollar-turnover field exists. The site therefore ranks by the labelled estimate volume_fp × last_price_dollars and shows the contract volume beside it. Get Markets · Fixed-point representation
How does an event resolve, and how is that recorded? Binary contracts settle YES or NO. A settled market reports result = yes or no, settlement_value_dollars ($1.0000 for YES, $0.0000 for NO) and settlement_ts. The resolution table on the dashboard and the category pages read exactly these fields. Market settlement · Get Markets
How is liquidity reported? GET /markets/{ticker}/orderbook returns orderbook_fp.yes_dollars and orderbook_fp.no_dollars, each a list of [price_dollars, count_fp] pairs sorted ascending. Only bids are published: a NO bid at $Y is an implied YES ask at $1.00 − $Y. An empty book is a valid response. Orderbook responses
How is a request signed? The signed message is timestamp(ms) + HTTP method + path without query parameters. Ed25519 keys sign the message directly; RSA keys use RSA-PSS with SHA-256, MGF1-SHA-256 and salt length equal to the digest length. The signature is base64 and sent in KALSHI-ACCESS-SIGNATURE; the timestamp must be within 30 seconds of Kalshi's clock. API keys · Quick start: authenticated requests. This implementation is checked offline by tools/test_signing.py.
Can the portfolio be read without an account? No. Balance, positions, fills, settlements and order placement all require a signed request with a Kalshi API key, and a key can only be issued to a logged-in account. API keys · Creating and using a demo account
Is there official price history? Yes. GET /series/{series_ticker}/markets/{ticker}/candlesticks returns 1-minute, 1-hour or 1-day candles with OHLC in dollars, up to 5,000 periods per request. Timestamps are in seconds. Get Market Candlesticks
Is the demo data real? No. Kalshi states that prices and behaviour in the demo environment may not reflect real markets, and the demo contains synthetic contracts (“1+1 = 3”, “Demo only” hourly markets, “demo strike” contracts). Demo environment · observed demo responses in data/
Which status values are valid for filtering? The documented status filter values for GET /markets are unopened, open, closed and settled. Responses use different values (active, finalized), which is an inconsistency worth flagging (F4). Get Markets

Part B — Still missing, and how to discover it

Each item states what is known, what is missing, why it blocks a decision, and the concrete way to get it.

ID / topicWhat is missingHow to discover itWhat it blocks
Q1 · Demo account A Kalshi demo account, an API key id and the matching private key. None exist in this environment. Sign up at demo.kalshi.co/sign-up (mock personal details are allowed; an email address and password are still required, so it cannot be automated). Then create a key and run python3 tools/kalshi_trade.py --key <key.pem> --key-id <KEY_ID> balance. Every account figure: balance, positions, fills, settlements, executed trades and all per-trade performance numbers. This is the only hard blocker on the site.
Q2 · Fee schedule The official Kalshi fee formula and the per-series parameters that feed it. Read the fee documentation linked from the API reference, and read fee_type / fee_multiplier on each series (both are already captured in data/series_scope.json). Net P&L, win-rate versus return comparison, and any claim that one strategy is better than another. Until this is read, every P&L on the site is gross and labelled as such.
Q3 · “Gas prices” definition Whether crude-oil and refined-product contracts (Commodities “Oil & Gas”) belong in scope alongside retail gasoline and diesel contracts (Economics “Oil and energy”). List the matching series on the gas page (each row links to its series record) and mark the ones to keep. The category pages already show the exact basis used for every row. Which rows belong on the gas page and therefore in the “highest dollar amount” ranking.
Q4 · “Culture” definition Whether “culture” means only the Entertainment category, or also celebrity/politics markets that a reader would call cultural. Same method as Q3, on the culture page. The published taxonomy contains Entertainment and no “Culture” category, which is why the mapping is explicit on the page. The culture page contents and the topic split of the ranking.
Q5 · Dollar window Whether “highest dollar amount” means lifetime turnover or the last 24 hours. Both columns are already collected (volume_fp and volume_24h_fp). Suggestion S1 proposes showing both and sorting by the 24-hour estimate by default. The default sort order of the dashboard table.
Q6 · Rate limits The published request limits for the demo API. Read the rate-limit documentation. The collector already records the status of every request it made in data/collection_log.json, which would show a 429 immediately. Safe polling cadence for the live dashboard and for the scheduled collector.
Q7 · WebSocket authentication Whether the ticker channel requires an authenticated handshake even for public markets. Read the WebSocket quick start. The dashboard does not depend on it — the chart works from REST polling plus candlesticks — but a confirmation would let the site use the streaming feed for second-level updates. Whether second-resolution live ticks can be added without credentials.
Q8 · Browser access (CORS) Whether a page on karagemop466-tech.github.io can read the demo API directly. Open the published dashboard and read the status line: it states either “Live: …” or “Snapshot mode: …”. If it reports snapshot mode, the published pages are serving the committed snapshot instead. Nothing is blocked — the snapshot fallback exists — but it changes how fresh the page is.
Q9 · Synthetic demo contracts Which demo markets are synthetic and should be excluded from any statistic. Rule-based detection on rules_primary, title and strike_type (suggestion S8), then a reviewed allow/deny list kept in the repository. Any win-rate or P&L statistic computed from demo fills.
Q10 · Settlement-source quality Which settlement sources are good enough to trade a market whose outcome cannot otherwise be checked. Score the settlement source lists already captured per series (suggestion S9). The observed placeholder and search-engine links are listed on the Flagged for Review page. Whether a market is eligible for the dashboard’s “tradeable” shortlist.
Q11 · Risk limits The maximum contracts per order, per topic and in total, and the maximum time a position may be held. A decision only the account owner can make. Suggested starting values are given on the Suggestions page; they are not applied by the site. Safe operation of the order form once an account is connected.
Q12 · Resolution timeline When each market moved from open to settled, not just that it is settled now. Keep the scheduled collector's snapshots and diff them (suggestion S5). The collector already commits data/ every two hours. “Tracked until the event resolved” over time, rather than a single end state.
Q13 · Clock synchronisation Confirmation that the machine running the CLI is within 30 seconds of Kalshi's clock. Run date -u against a time service, or simply run the CLI once: a 401 header_timestamp_expired response means the clock is off. Order submission from the command line.
Q14 · Where the site is served from Whether the final site lives at the repository root or under a docs/ folder, and whether the Pages workflow should publish the built site or the raw repository. Both layouts exist in the repository history. The current Pages workflow publishes the repository root, which is where the consolidated site lives. The final URL and the links between pages.

Part C — Questions that are not open

  • Does the demo environment use real money? No. Demo and production credentials are separate and the demo uses mock funds. Source
  • Can a market be both open and settled? No — the status filter separates them (open versus settled), and the response status is active or finalized. Source
  • Do we need to pay for market data? No authentication is required for GET /markets, GET /events, GET /series, GET /markets/{ticker}, GET /markets/{ticker}/orderbook or the candlesticks endpoint. Market data quick start
  • Is the ranking in dollars or contracts? It is a documented estimate, labelled as such on every table that shows it, because the API has no dollar-turnover field (Q5, F-10).
