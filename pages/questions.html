Questions, information and answers

Before any decision can reasonably be made, the questions below have to be answered. For each one the table states what is already known (with the official source), what is still missing, and how to obtain it. “Open” means the answer is not yet established; “Answered” means it is settled by an official source that is linked.

Q1 Which exact endpoints should the site call, and are they demo-only? The demo REST base is https://external-api.demo.kalshi.co/trade-api/v2 (recommended) with https://demo-api.kalshi.co/trade-api/v2 also supported; WebSocket bases are wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 and wss://demo-api.kalshi.co/trade-api/ws/v2. Demo credentials are not shared with production.
API Environments and Endpoints · Test In The Demo Environment		 Nothing. — answered Nothing
Q2 Which calls need authentication, and how are requests signed? Public market data needs no authentication. Authenticated calls need three headers, a millisecond timestamp and a base64 signature over timestamp + METHOD + path (query string excluded), using RSA-PSS/SHA-256 or Ed25519; the timestamp must be within 30 seconds of Kalshi’s clock.
Authenticated Requests · Market Data (no auth)		 Whether the browser build environment allows the demo host on port 443 — this could not be tested here (see the Flagged for Review page). Open the published site from a normal browser and press Go live; the status line reports the exact failure if it is blocked. partly answered Whether the live path is usable at all
Q3 What is the correct way to place an order on the current API? POST /portfolio/events/orders with side = bid/ask, count, price as a fixed-point dollar string, time_in_force and self_trade_prevention_type. The legacy /portfolio/orders write endpoints were removed and now return 410 Gone.
Create Order (V2)		 How a NO-side order should be quoted: the order direction guide maps bid ≡ yes and ask ≡ no, and the order-book guide shows a YES bid at $X is a NO ask at $(1 − X); the site converts NO prices as 1 − price and shows the conversion, but no live order was executed here, so the convention is untested in practice.
Order direction		 Place one demo order on a market with a visible book in the demo account and confirm the resting side and price from GET /portfolio/orders; if the side is wrong, a resting (non-crossing) order shows it without a fill. partly answered Automated trading, strategy automation
Q4 Which price should a “NO” order use? Direction does not change the price: an order at price p on one outcome matches an order at the same price p on the other outcome.
Order direction		 Whether the single V2 book quotes prices in the YES leg for both sides — the V2 reference calls it a “single-book bid/ask side” but does not restate the price scale in the same sentence. The same one-contract resting-order test as Q3, plus GET /markets/{ticker}/orderbook before and after, to see which level the order lands on. open Automated trading, strategy automation
Q5 Does the API publish a dollar volume or dollar turnover field? No. The market response exposes contract counts (volume_fp, volume_24h_fp, open_interest_fp), dollar prices and a notional_value_dollars field that is reported as 1.0000 on ordinary binary markets in the demo environment.
Get Markets		 Whether Kalshi publishes an authoritative dollar-turnover definition elsewhere (for example in the historical API or the FIX feed) that should be used instead of the site’s own formula. Search the official API reference for a dollar-volume field; if none exists, keep the computed metric and label it as computed (already done on the Methodology page). partly answered Nothing — the computed metric is already labelled
Q6 How should the five topics be defined? Kalshi publishes series category and tags, but no “gas / culture / golf” grouping.
Get Series List		 Whether the intended scope is by series, by event, or by settlement source — for example whether the NVIDIA/AI series should count as “culture”, and whether all sports or only golf should be in scope. A one-line scope decision from the requester, recorded on the Suggestions board, then applied in both implementations (scripts/refresh-data.mjs and assets/common.js). open Every ranking and count on the site
Q7 How long should a market be tracked before it is considered “resolved”? The API reports status, result, settlement_value_dollars and settlement_ts; settlement “typically” happens shortly after expiration but timing varies.
Market Settlement · Market Lifecycle		 Nothing technical — the site uses the official result field as the single definition of “resolved”. — answered Nothing
Q8 Can the WebSocket feed be used directly from a browser? The handshake requires API key headers, and the docs list only ticker, trade and lifecycle channels as public — but the connection itself is still authenticated.
Quick Start: WebSockets		 Whether Kalshi supports passing the signature as a query parameter or sub-protocol, which would make the feed usable from a static page without a proxy. The docs consulted do not state either way. Ask Kalshi support / check the WebSocket reference for query-parameter authentication; meanwhile the site uses REST polling and says so. open Latency and rate-limit budget of the live feed
Q9 How should the demo account’s performance be measured? Balance and portfolio value come from GET /portfolio/balance; positions, fills and orders from the corresponding portfolio endpoints; each fill carries fee_cost.
Get Balance · Get Fills		 No account-level history exists yet — the account has no fills, so there is no realised track record to analyse. Place demo orders in the demo account, let some of them settle, then re-run the Trade analysis page; the categorisation rules are already implemented and will populate automatically. open Any conclusion about strategy quality
Q10 What should a “strategy” be allowed to say? Nothing in the API defines a strategy. The site’s rule is documented: a segment needs at least three fills in settled markets before it is written up. Whether the requester wants strategies restricted to the five topics, to a maximum risk, to a minimum sample size larger than three, or to specific order types. A decision on the Suggestions board (S6) and a matching change to the analysis rule. open The strategy section of the analysis page
Q11 Which external probability source should be used to judge a contract price? Nothing in the Kalshi API provides an outside probability estimate. Everything: which source, what licence, what refresh rate, and how disagreements are displayed. Decide one source per topic and record it with a citation (Suggestions S10). Until then the site shows only Kalshi’s own prices and makes no edge claims. open Any “is this mispriced?” judgement
Q12 How fresh must the data be, and what is acceptable downtime? The API documents rate limits per endpoint and the exchange status endpoint reports exchange_active / trading_active.
Rate Limits and Tiers · Get Exchange Status		 The acceptable staleness threshold and whether a stale snapshot should be visually flagged. Pick a threshold (for example, “flag anything older than 30 minutes”) and implement it on the dashboard status line. open Trust in the live views
Q13 Should the site also track production markets? Production uses https://external-api.kalshi.com/trade-api/v2 and credentials that are never shared with demo.
API Environments and Endpoints		 Whether production read-only data is wanted (public market data needs no key) and whether demo-only wording stays. A decision, then a base-URL switch on the dashboard (Suggestions S11). open Whether the dashboard stays demo-only
Q14 Where should the trade log live? Nothing in the API requires it; GET /portfolio/fills and GET /historical/fills exist, the latter for archived fills.
Get Historical Fills		 Whether the browser-local log is enough, or whether an export (CSV) and an external store are needed for longer-term review. Decide in review; the local log is already CSV-shaped and can be exported from the browser. open Long-run performance tracking
Q15 Is it safe to put a private key into a public web page? The key is used client-side to sign requests; Kalshi’s own quick starts keep the key in the user’s process. Demo keys have no cash value.
API Keys		 Whether the requester will ever use a production key here — if yes, a different deployment (local-only tool) is required. Confirm the intended environment. If production is ever involved, do not use this static site. partly answered Deployment target
