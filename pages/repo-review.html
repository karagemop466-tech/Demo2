Repo review — line by line

What was in this repository before this session, what was wrong with it, and what was changed. Findings are ordered by severity: R3, R4, R5 and R6 are defects that prevented a requested feature from working at all.

Most serious finding (R3). The previously published build sent every demo order to POST /portfolio/orders. The official documentation states that path has been removed and returns 410 Gone, so trade execution could not have worked. The implementation now targets POST /portfolio/events/orders.

R12repository (workflows)Five workflows write to main, each with its own concurrency group
Concurrency keys are kalshi-refresh (every 10 min), pages-and-data (7,22,37,52 past the hour), collect-kalshi and data-refresh (both at 23 past every second hour), and kalshi-portfolio (hourly at :20). GitHub serializes only runs that share a key, so these runs can overlap and push to main at the same time. Source: GitHub docs: control workflow concurrency; the workflow files in .github/workflows/.		Push races on the same data files; the result depends on which run pushes last.Flagged. Serializing all data writers under one key is the recommended fix. Not changed here (cross-session files).
R13repository (workflows)Bots push generated data straight to main, and one rebase failure is swallowed
Four workflows push to main without a pull request: pages.yml (line 59), refresh-data.yml (line 88), trade.yml (line 100) and collect.yml (line 46, using GITHUB_REF_NAME). collect.yml runs git pull --rebase ... || true, so a failed rebase is ignored and the push that follows can fail without any error being raised. Source: the workflow files in .github/workflows/.		Generated data bypasses review, which is acceptable only if the data cannot change code. A silent rebase failure can drop a snapshot without notice.Flagged. The fix is to remove || true and to fail the job when the rebase fails. Not changed here.
R14scripts/__pycache__Compiled bytecode is tracked in git
scripts/__pycache__/check_links.cpython-311.pyc and scripts/__pycache__/fetch_data.cpython-311.pyc are tracked, even though .gitignore lists __pycache__/. Checked with git ls-files | grep __pycache__ on this branch. Source: git docs: gitignore, NOTES: “To stop tracking a file that is currently tracked, use git rm --cached”.		Binary noise in diffs; a stale .pyc can differ from the source it claims to compile.Flagged. Fix: git rm --cached both files. Not changed here (the file belongs to another session’s scope).
