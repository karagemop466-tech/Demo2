Executive summary

One paragraph. This project collects, organises and analyses Kalshi demo markets in five topics only — gas prices, elections, culture, crypto and golf. It ranks those markets by dollar size, graphs contract price over selectable time scales, shows how many contracts rest at each price, follows watched markets until they resolve yes or no, and — when the user supplies their own demo API credentials in the browser — reads the demo account's balance, positions, fills and orders, places demo limit orders, and analyses the resulting fills by category. Every number on the site comes from the official Kalshi demo API or from a CI snapshot of it; nothing is estimated, and anything that could not be confirmed from an official source is left blank and published on Flagged for Review.

Key risks and constraints

Data and modelling risks

  • Demo prices are not real prices. Kalshi states demo prices “may not be reflective of those in real markets” (demo environment). No conclusion drawn here transfers to real money.
  • No official “dollar volume” field. The API returns contract counts and dollar prices, so every dollar figure on this site is a documented arithmetic combination of API fields. The formulas are on the Methodology page.
  • Topic scoping is a rule, not an official flag. Kalshi does not publish a “gas prices / culture / golf” taxonomy. This project derives one from the official series category and tags; each row records the rule that matched so it can be audited.
  • Demo orders can fill against synthetic liquidity. Fills recorded in the demo environment do not demonstrate real execution quality.

Security and operational risks

  • Keys stay in the browser. The private key is used with WebCrypto to sign requests and is kept in sessionStorage only — it is never written to this repository, never sent to any server but Kalshi, and is cleared when the tab closes.
  • This is a static GitHub Pages site. There is no server-side component, so there is no place to store credentials, and no way to run the signed calls for the visitor automatically.
  • WebSocket is not used for the live feed. The Kalshi WebSocket handshake requires signed headers, and browsers cannot set custom headers on a WebSocket. The live feed therefore uses REST polling; see Flagged for Review.
  • Rate limits. Balance reads are separately rate limited (Basic/Advanced: 1 call/second). The site polls conservatively and never loops tightly.

What must be decided before this is used for anything

Read Questions (open items and missing information) and Suggestions (proposals awaiting a decision). Nothing on this site changes on its own: the suggestion board is a review record, and no change is implemented until it is accepted there.
