Methodology

Every figure on this site comes from the Kalshi demo API, either read live in your browser or from the snapshot that the scheduled CI job writes into data/. This page states exactly how each number is produced, so any row can be checked against its source.

The snapshot is produced by scripts/refresh-data.mjs, run by .github/workflows/refresh-data.yml on a schedule and on demand. It writes data/markets.json, data/resolved.json, data/series.json and data/meta.json. Each file records generated_at, the endpoints used, the page counts and whether pagination was truncated. A live read in the browser overrides the snapshot for the same fields.

2 · How the five topics are selected

Kalshi does not publish a “gas prices / culture / golf” taxonomy, so this project defines one and records the rule that matched for every row. For each market the rules are applied in this order, and the first match wins:

  1. Official category. The series’ category (or the event’s category) is compared with the topic’s category list.
  2. Official tag. The series’ tags array is searched for one of the topic’s tag words.
  3. Series title, then event title, then market title word matches.

The same rule list is implemented twice — once in scripts/refresh-data.mjs (server side) and once in assets/common.js (browser side) — so a live read and the snapshot classify identically. Every published row carries its own topic_rule string, shown in the “Topic & why” column of the dashboard table.

3 · The “highest dollar amount” metrics

The market response has contract counts and dollar prices but no single dollar-volume field (Get Markets schema). Four dollar measures are therefore published, each computed from documented fields, and the dashboard lets you rank by any of them:

MetricFormulaAPI fields usedMeaning
Turnover $volume_fp × last_price_dollarsvolume_fp, last_price_dollars Lifetime traded notional at the last traded price — an approximation, because trades happened at many different prices.
24 h $volume_24h_fp × last_price_dollarsvolume_24h_fp, last_price_dollars Same idea over the last 24 hours — the most “live” of the four.
OI value $open_interest_fp × last_price_dollarsopen_interest_fp, last_price_dollars Mark-to-market value of contracts still open.
Resting $Σ (price × contracts) over order-book levels, YES bids + NO bids order-book levels from GET /markets/{ticker}/orderbook Liquidity available at the current book — the executability measure. Computed for the top markets of each topic only, because it needs one request per market.

The API’s own notional_value_dollars field is also carried through verbatim for reference, but it is reported as 1.0000 on ordinary binary markets in the demo environment, so it is not used as the ranking metric. That observation is recorded on the Flagged for Review page. Prices and counts are fixed-point strings (*_dollars / *_fp) — Fixed-Point Representation.

5 · Liquidity, spread and implied ask

The order-book endpoint returns bids only, because in a binary market a YES bid at $X is a NO ask at $(1 − X). The dashboard therefore shows:

  • Best YES bid — the highest price in orderbook_fp.yes_dollars.
  • Implied YES ask — 1 − (highest price in orderbook_fp.no_dollars).
  • Spread — implied ask minus best bid.
  • Contracts available at each price — each level with its contract count, cumulative contracts and cumulative dollars.

Source: Orderbook Responses.

6 · Resolution and trade results

  • A market settles to yes or no; holders of the winning outcome receive $1 per contract (Market Settlement).
  • Settlement timing varies with market type and data availability, so the tracker keeps polling until the API reports a result.
  • P&L for a resolved fill = contracts × (1 − entry price) for a winning YES fill, contracts × (0 − entry price) for a losing YES fill, and the mirrored form for NO fills. Fees are taken from the exchange’s own fee_cost field on each fill.
  • A strategy is only written down when a segment contains at least three fills in settled markets.

7 · What this methodology deliberately does not do

  • It does not infer, estimate or fill in any value. If the API does not return a field, the cell shows “—”.
  • It does not mix demo data with production data, and it never uses real funds.
  • It does not claim that demo outcomes predict real ones — Kalshi warns that demo prices and behaviour “may not be reflective of those in real markets” (demo environment).
  • It does not back-test on a market universe that was chosen after the fact.
