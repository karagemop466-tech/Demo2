Suggestions — review and choose before anything changes

Each suggestion states the problem, the proposed change, the evidence behind it and the cost of doing it. Record a decision with Approve / Defer / Reject. Decisions are stored in this browser only; the site is not modified by a decision, and nothing listed here has been implemented unless it is marked implemented.

S1 · Give the dashboard a real dollar-turnover ranking proposed

Problem. The request is for “highest dollar amount” markets, but the API reports volume in contracts (volume_fp) and exposes no dollar-turnover field, so the current ranking uses the estimate volume_fp × last_price_dollars.

Proposal. Rank by volume_24h_fp × last_price_dollars as a second column, and show both 24-hour and lifetime volume so a single quiet day cannot hide an active market. Label both as estimates.

Evidence. Get Markets field list. Cost. Low — one extra column and one sort.

S2 · Turn the chart into a real history, not only live points implemented

Problem. A chart built only from browser polling has no history before the page was opened, and cannot show anything at seconds resolution.

Proposal. Use the official candlestick endpoint for the selected market — 1-minute, 1-hour or 1-day candles depending on the window — and layer live polled points on top. This is already implemented on the dashboard.

Evidence. Get Market Candlesticks — period intervals 1, 60 and 1,440 minutes, max 5,000 periods per request. Cost. Done.

S3 · Record the orderbook at the moment of every order proposed

Problem. Slippage and “did we take the offer or the bid” cannot be answered from fills alone, because the book changes between the order and the fill.

Proposal. When an order is placed from the browser, save the orderbook snapshot returned by GET /markets/{ticker}/orderbook at that instant alongside the trade, and compute the entry side of the book from it.

Evidence. Orderbook responses — bids only; implied ask = $1.00 − best NO bid. Cost. Low.

S4 · Confirm the Kalshi fee schedule and make P&L fee-aware proposed

Problem. Every P&L figure computed from entry price and settlement value is gross. Kalshi charges a fee that depends on the series' fee_type and fee_multiplier, so two markets with the same price move can have different net results.

Proposal. Read the fee schedule from the official fee documentation, reproduce the formula per fee_type, and report net P&L alongside gross.

Evidence. fee_type and fee_multiplier are present on the series records; the fee schedule itself has not been read in this session (see Q8). Cost. Medium.

S5 · Store the snapshot history so "resolved" can be tracked over time proposed

Problem. The site shows markets that have already settled, but it cannot show when a market that was open yesterday resolved, because each collection only records the current state.

Proposal. The scheduled collector already commits a snapshot every two hours. Keep the history (one file per collection, compressed) and diff consecutive snapshots to produce a genuine “open → resolved YES/NO” timeline per market.

Evidence. .github/workflows/collect.yml already commits data/ on a schedule. Cost. Low to medium — needs retention policy and storage budget.

S6 · Replace the topic keyword fallback with an explicit, reviewed scope proposed

Problem. Markets are matched to a topic by their series category and tags first, but a keyword fallback is used when a market carries no series metadata. That fallback is a judgement call and can pull in an unrelated market.

Proposal. Show every keyword-matched row with a visible basis column (already added), and keep a reviewed allow/deny list of series tickers per topic that overrides the keyword rule.

Evidence. The basis column and the classification rule are visible on the category pages and recorded in tools/collect_kalshi.py. Cost. Low.

S7 · Decide where account credentials are allowed to live needs your decision

Problem. Trade execution needs a Kalshi API key. A public static site cannot hold a server-side secret, and a browser-side signer means the key is loaded into a page served from a public URL.

Proposal (three options). (a) local command line only, as shipped in tools/kalshi_trade.py; (b) browser signer behind an explicit acknowledgement, as shipped on the Portfolio page; (c) a private server-side service with the key in a secret manager, reachable only by you — the strongest option if this ever leaves the demo environment.

Cost. (a) zero, (b) zero, (c) requires hosting and a secret manager. This is the one item where the site currently offers more than one behaviour and only you can pick.

S8 · Separate synthetic demo markets from the analysis proposed

Problem. The demo environment contains markets such as “1+1 = 3”, “Demo only” crypto hourly markets and contracts with a “demo strike” field. They resolve deterministically and would otherwise dominate any win-rate calculation.

Proposal. Tag every market whose title, rules or strike type indicate a synthetic contract, and exclude those rows from category statistics while keeping them visible and labelled.

Evidence. Observed in the demo responses, e.g. the “Demo only. YES if the Coinbase Exchange BTC-USD one-minute candle …” rule text and strike_type: custom with a “demo strike” value. Cost. Low.

S9 · Add settlement-source quality scoring to the category tables proposed

Problem. Some demo series publish placeholder settlement sources (free-text names with a kalshi.com link) or a search-engine URL, which makes the resolution hard to verify afterwards.

Proposal. Score each series' settlement sources (named official source · third-party data site · placeholder · search engine) and show the score, so markets whose outcome cannot be independently checked are visible before they are traded.

Evidence. Settlement source lists are captured per series in data/series_scope.json and rendered on the category pages; the observed irregularities are listed on the Flagged for Review page. Cost. Low.

S10 · Put the whole thing behind a read-only default implemented

Problem. A live site that can place orders can be surprising.

Proposal. Order entry is only reachable after an explicit connection step, and the dashboard itself is read-only. Implemented on the Portfolio page.

Cost. Done.

How a decision is used

A decision is a review input, not an automation. “Approve” means the change should be implemented and re-verified against the official API before the site is updated; “Defer” means the proposal stays open; “Reject” means the proposal is closed with your reason recorded in COORDINATION.md. The exported JSON file is the hand-off to the next session.
