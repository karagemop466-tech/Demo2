Q1 · Where do demo API credentials come from — and can they ever be entered in this site? answered (security) · automation gap remains
Answer (official + repo policy): keys are created at demo.kalshi.co → Account & security → API Keys → Create Key (API Key ID + one-time PEM download) — official instructions. They must never be typed into a public web page — repo README safety notice + open PR #6 (flag F-17, decision D-05). This site's credential-paste UI was removed at integration.
Approved execution paths: (1) run the repo server/ backend locally with environment variables (KALSHI_ACCESS_KEY/KALSHI_PRIVATE_KEY — gitignored), (2) official docs “Try it” console, (3) your own script using the official signing recipe. The Trading page now emits the exact V2 body + signed curl export for those paths.
Still-missing input (automation): this build session has no keys anywhere in its environment, so no orders/fills/settlements could be pre-executed or pre-populated — personal portfolio tables stay blank by rule (F-02).
Q2 · Which hosting topology is acceptable for a WebSocket/proxy feature? missing input
Answer (official): WS needs a signed auth handshake with custom headers (WS quickstart); browser WebSocket cannot send custom headers, and GitHub Pages serves static assets only.
Decision needed: (a) accept REST polling (current, decision D-02), or (b) approve a small relay (S-01) and say where it runs + how its key is stored. How to discover: owner policy on external services & secrets — no doc page can answer this.

Decision needed: keep culture → Entertainment (current, flagged F-12), fold Social in, or split sub-tabs. How to discover: inspect series?category=Social (not yet fetched) to see whether Social holds anything beyond Entertainment before deciding.

Answered from official sources

Q4 · What are the correct demo endpoints? answered
REST https://external-api.demo.kalshi.co/trade-api/v2 (also https://demo-api.kalshi.co/trade-api/v2); WS wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 (also wss://demo-api.kalshi.co/trade-api/ws/v2). Verified live: GET /exchange/status → 200, trading active. Source: docs · demo environment.
Q5 · How do we rank “highest dollar amount” events without a server-side sort? answered · with flag
The Market schema has no dollar-turnover field and /markets has no sort-by-volume parameter (verified in Get Markets spec). Approach: fetch, then rank client-side by volume_24h_fp × last_price_dollars, labelled derived in every view (F-01, decision D-03), with official contract-count columns always shown alongside.
Q6 · How does an event resolve and who pays what? answered
Market result ∈ yes|no|scalar; winners receive $1/contract, losers $0; simple determinations have zero settlement fee; payouts settle after expiration + settlement_timer_seconds. Verified field examples on the Events & Resolutions page; rules: Market Settlement.
Q7 · Can this page poll the demo API directly from visitors' browsers (CORS)? answered at runtime
Cannot be pre-verified from the build sandbox (network allowlist). The dashboard probes GET /exchange/status on load: success → LIVE mode with polling; failure → SNAPSHOT mode with bundled verified data. The displayed mode is always truthful, so CORS behaviour needs no assumption either way. Source endpoints: probe URL.
Q8 · What are the rate limits for market-data polling? partial — one number verified
Verified: GET /portfolio/balance has its own bucket — Basic/Advanced tiers 1 request/second (higher tiers 5/s), and docs advise reacting to fill events instead of polling balance — Get Balance. Responses across market data are cached server-side for a short time — Get Markets.
Missing: numeric Read-budget numbers were not fetched this session (rate-limits docs page exists: docs · rate limits) — dashboard conservatively polls every 60 s and shows fewer than ~30 requests per refresh. Decision it gates: raising refresh frequency / running S-03 crawls — confirm budget there first.
Q9 · Which event should be tracked “to resolution” first? answered
The tracker follows all open watchlist events (live mode polls status transitions) — so no pick is required. Nearest observed deadlines at collection: KXWTIH-26NOV2007 strike 2026-11-20T12:00:00Z, KXWTIW-26NOV2014 close 2026-11-20T19:30:00Z, KXBTC-26NOV2007 close 2026-11-20T12:00:00Z (hourly crypto settles each hour). Sources: events table rows.
Q10 · What precision do the chart axes need? answered
Candlesticks support only 1/60/1440-minute periods (spec), so seconds granularity uses trade prints with millisecond timestamps (Get Trades: min_ts/max_ts in seconds). Chart X-axis exposes Seconds/Minutes/Hours/Days accordingly; Y-axis is the YES contract price in dollars (fixed-point strings, e.g. 0.0500).
Q11 · Can we place and cancel orders through this site? answered · gated by Q1
Create: POST /portfolio/events/orders (V2 body verified field-by-field — spec). Legacy /portfolio/orders writes are gone (410). Cancel: V2 cancel endpoint exists in docs (Cancel Order V2) but was not exercised this session (no keys) — listed honestly on the Trading page rather than faked.
Q12 · Does the API provide long-term history beyond the live data set? answered (not yet used)
Yes — docs reference GET /historical/fills and GET /historical/positions for records before the historical cutoff / after archival — docs · historical data. Schemas were not fetched this session, so no table here uses them (would violate the source rule). Needed when: performance window exceeds live retention. Next step: fetch those two spec pages before building the long-horizon view.

Q14 · Are demo numbers safe to present as real market facts? answered — no
Officially: “The price and behavior of markets in the demo environment may not be reflective of those in real markets” — demo docs. The site therefore labels the environment everywhere and flags implausible demo volumes (F-08) instead of normalising them away.
