Trading, strategies and performance

What the repository can and cannot do on a Kalshi demo account, and how trades are categorised so a strategy can be tested against evidence rather than opinion.

No account values are shown on this page. Portfolio, positions, fills and order placement need a Kalshi API key. No key exists in this repository and none was invented, so every value below is a dash and flagged. The three gates that must all open before a demo order is sent are listed under Execution policy.

Execution policy

Three independent gates must all be open before the repository will send a demo order.

  1. Repository secrets KALSHI_DEMO_API_KEY_ID and KALSHI_DEMO_PRIVATE_KEY exist — see API keys.
  2. Repository variable KALSHI_TRADING_ENABLED=1 is set.
  3. The order passes the executor's checks: the ticker is in the collector's in-scope set, no duplicate tickers, and the order is inside the per-run notional cap.

Orders use the documented V2 endpoint POST /portfolio/events/orders (Create Order (V2)). The legacy POST /portfolio/orders returns 410 Gone and is not used. No browser page in this repository asks for a private key.

How trades are categorised

Every trade is labelled on four axes so that a strategy is proposed only when the evidence supports it. A bucket needs at least 10 trades before a pattern is described.

AxisValuesWhy it matters
Topicgas, elections, culture, crypto, golfBehaviour differs by topic; the same price level means different things in each.
Sideyes, noA no contract at price p is economically a yes contract at 1 − p, so the side changes the risk, not just the direction.
Price band0.00–0.10, 0.10–0.40, 0.40–0.70, 0.70–1.00Long shots pay differently from favourites; the bands are read from the contract price, not from the outcome.
Topic × sidethe cross of the two axes aboveShows where an edge, if any, actually concentrates.
